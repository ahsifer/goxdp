# Introduction

As the number of GoXDP instances increases, The effort needed and the complexity to manage these instances increases. Therefore, The GoXDP Master-Slave cluster setup can be effectively used to ease the propagation process of newly blocked/allowed subnets and IP addresses to all slave nodes as shown in the following diagram. <br>
![master-slave](uploads/6def4ec3bfa40442960eb265430a14cc/master-slave.png){width=70%}

# Configuration files

The master service needs the following files:

1. blocked.list
2. auth.json
3. internal.json

## blocked.list file

This file include list of the IP addresses that needs to be blocked forever by the slave nodes. The contents of the file can be as follows:

```
192.168.1.1
10.4.4.0/24
123.159.0.0/16
1.1.1.1/32
5.4.3.2/32
```

## auth.json file

This file include list of the users that are allowed to interact with the master service. Also, it is used by the internal logging service of the master service to log the name of the user when interacting with the master service. The content of it can be as follows:

```
[
	{
		"USERNAME":"ahsifer",
		"TOKEN":"xxxxxxxxx"
	},
	{
		"USERNAME":"sam",
		"TOKEN":"xxxxxxx"
	}
]

```

## internal.json file

As the PULL_COUNTER and the list of CLI blocked IP addresses will reset when the master service restart or the entire server crushed, the internal.json is an auto generated file that is used to solve this issue by storing the value of the PULL_COUNTER and the list of the blocked IP addresses with their timeouts that are blocked by CLI or RESTful API requests to save them across restarts. The following is a sample of the file contents.

```
{
	"PULL_COUNTER": 7929,
	"CLI_BLOCKED": [
		{
			"src": "1.1.1.2/32"
		},
		{
			"src": "127.0.0.2/32",
			"timeout": 496
		}
	]
}
```

# Master-Slave communication process

1. When the master service starts for the first time, it reads the contents of blocked.list and auth.json files and then it creates the internal.json file if it does not exist and initiates the PULL_COUNTER. This counter exists on both master and slave nodes. The initial value of the counter is 1 for the master and 0 for the slave nodes.
2. The internal.json configuration file is auto-generated by the master service and is used to store the value of the PULL_COUNTER and currently blocked IP addresses. Therefore, when the master service restarts, it will read the value of the PULL_COUNTER and the CLI_BLOCKED list. Any operation on the master service will lead to rewrite the content of the file to ensure it stores the latest value of the PULL_COUNTER and the CLI_BLOCKED list.
3. Each slave node will pull the value of the PULL_COUNTER from the master node using restful API requests. If the returned value is different than the value of the slave's PULL_COUNTER, the slave node will pull the blocked IP addresses and subnets from the master and will block and unblock accordingly and then update its own PULL_COUNTER.
4. Any operations on the master including block, allow, flush, increment, and reload will lead to an increment of the PULL_COUNTER so that the new configuration is propagated to the slave nodes.
5. It is crucial to mention that the slave nodes have higher priority than the master in terms of IP address blocking. This means if the IP address is blocked directly on the slave node, it cannot be unblocked by the master. This will ensure that the system fulfills the requirements when specific IP addresses need to be blocked on specific slave nodes forever.
6. when blocking with timeout for instance blocking 1.1.1.1/32 for 120 seconds and one of the slave nodes lost the connectivity with the master for 30 seconds. When the issue is resolved the slave node will block the 1.1.1.1/32 IP address only for 90 seconds.
